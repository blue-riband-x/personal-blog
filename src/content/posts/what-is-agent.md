前几天有人问我：Agent 和 ChatGPT 到底差在哪？

我想了想，最省事的回答是这样的——

你跟 ChatGPT 说"帮我把这周的报销记到表格里"，它给你一段整理好的文字，然后你自己复制、打开表格、找到那一行、粘贴进去。

你跟 Agent 说同一句话，它会自己打开表格、找到那一行、填进去，然后回来跟你讲："记好了。不过周三那笔你没写金额，我按 38 块记的，对吗？"

差别不在它更聪明。差别在于，**它有一双手，而且它自己决定下一步做什么。**

这句话基本就是全文的答案了。下面把我理解的细节摊开讲。

## 先把"会说话的"和"会干活的"分开

大模型这东西，说到底是一个函数：你给它一段文字，它给你一段文字。就这样。

它没有手，没有眼睛，不能点鼠标，不能读你硬盘上的文件，也没法真的去 ping 一下服务器看看还活着没。你跟它说"帮我看看这台机器还能不能连上"，它只能根据训练数据里关于服务器的一般常识，给你编一段听起来很专业的话——因为它根本没有能力去做那件事。

后来产品上加了一堆东西：联网搜索、代码解释器、插件。看起来像能干活了，但仔细看流程你会发现：**什么时候搜、搜完之后怎么答，都是产品经理提前写死的。** 你问一句，它答一句，中间夹一次固定动作，结束。

Agent 的转折点只有一句话：**下一步做什么，不再由人预先排好，而是由模型自己根据当前情况决定。**

## 它到底是怎么"决定"的

没什么玄学，用的还是模型最本来的能力——预测接下来该输出什么。

只不过工程师把输出内容从"一段回答"换成了"我要调用哪个工具、参数填什么"。比如你问"北京明天要带伞吗"，它输出的可能是这么一段东西：

```json
{ "tool": "get_weather", "args": { "city": "北京", "date": "2026-10-22" } }
```

外面那层程序看到这个 JSON，就去真调接口，把结果拿回来塞回对话里。模型看到"明天小雨，12 到 18 度"，才输出人话："带吧，明天有小雨。"

这个思路 2022 年就有论文写过，叫 ReAct，Reason 加 Act，边想边做。火了三年多，剥掉包装看，内核朴素得有点好笑：**让模型一边想一边动手，动手的结果再喂回去让它继续想。**

## 一个循环，四个动作

写成循环就是四个动作：

**想 → 做 → 看 → 再想。**

- **想**：拿着目标和已经发生的事，判断现在还缺什么。
- **做**：挑一个工具，把参数填好，发出去。
- **看**：把工具返回的结果读进来，不管是数据还是一句报错。
- **再想**：够了吗？没够就继续，够了就收工。

它停下来只有两种情况：模型自己认为任务完成了（表现就是不再调工具，直接给你一段最终答复），或者撞上了步数上限、超时、被人按了停止。

所以如果有人问你"Agent 是什么"，最准确、也最短的回答就是：**一个带工具、会自己转圈的模型。**

没有比这更本质的定义了。剩下那些"自主规划""多智能体协作""反思机制"，都是在这个圈里加料。

## 三个零件，缺一个都跑不起来

**大脑是模型。** 它得足够聪明，能看懂工具是干嘛的、参数怎么填、结果说明了什么。小模型经常连 JSON 格式都写不对，让它在三个工具里选一个就选错，这种硬伤没法靠 prompt 修。

**手是工具。** 搜索、读写文件、跑命令、调接口、操作浏览器，都是。这里有个新手特别容易忽略的点：**工具的说明文字比工具本身还重要。** 模型只能靠那段描述判断"现在该不该用它"。两个功能一样的函数，一个注释写"查询订单"，另一个写"按手机号或订单号查订单，用户提到'我的快递''买了什么'时用"，后者被正确调用的概率天差地别。

**记性是上下文。** 它得知道自己刚才做过什么、哪一步失败了，不然会原地转圈。但上下文窗口是有限的，全塞进去会爆，丢太多会失忆。很多人做出来的 Agent 转两圈就开始重复上一个动作，八成是历史记录写坏了——要么漏了工具返回，要么把中间过程截断了。

## 拿一个真实任务跑一遍

假设你说："把项目里所有 console.log 删掉，删完跑一遍测试。"

第一轮，它想：得先找出哪些文件里有。于是 `grep -rn "console.log" src/`，拿到 17 个文件。

第二轮，它想：一个个改太慢，先看引用最多的那个。于是读 `src/lib/utils.ts`，拿到内容。

第三轮，它判断这段可以删，于是写文件。改完第一个，接着下一个。

跑完十几轮之后，它想：都改完了，该验证了。于是执行 `npm test`，结果 3 个失败。

接下来是分水岭。好的 Agent 会去读失败日志，发现是自己删掉了一行有副作用的日志调用，改回去再跑；差的 Agent 会开始瞎改，越改越乱，最后把测试也改绿了——这在业界有个专门的词，叫"作弊"。

这个例子想说的事是：**Agent 不是一台给你正确答案的机器，它是一个会犯错的执行者。** 你的工作不是求它别犯错，而是给它设计好护栏：改文件前先 commit、跑完必须过测试、危险操作要人确认。

## 那 Workflow 和 Agent 到底差在哪

这个问题面试里特别常问，其实判断标准特别朴素。

Workflow 是**人定顺序，机器执行**。你把流程写死：先检索、再重排、再生成、最后校验。每一步的输入输出都是确定的，出问题能精确定位到某个环节。

Agent 是**人定目标，机器定顺序**。走哪条路、走几步、什么时候停，都是模型现场决定的。

这两者没有谁更高级。Workflow 稳定、便宜、好调试、可预测；Agent 灵活，但每一步都在赌，错误会累积放大。

我自己用的判断法是：**你能把这事的流程图在白板上画出来，就写 workflow；画不出来，才上 Agent。**

这也是为什么市面上很多号称 Agent 的产品，拆开看其实是个 workflow，只在中间一两个节点让模型自由发挥。这不丢人，通常还是工程上更正确的选择。

## 它为什么经常不靠谱

这点值得单独说，因为它决定了你到底该怎么用它。

假设模型每一步的准确率有 95%，听起来很高。但一个任务要走 10 步，全程都不出错的概率是 0.95 的 10 次方，大约 60%。走 20 步，掉到 36%。

这就是误差累积。**步数越多，越不可靠**，跟模型多聪明关系不大。

所以真正有效的优化方向不是"让模型更聪明"（这事你也控制不了），而是这四条：

- 能一次调用解决的，别拆成五次。
- 每步都要有客观的验证手段：跑测试、跑类型检查、让工具返回结构化数据而不是一段散文。
- 失败要能回滚，至少用上 git。
- 关键节点必须插人——转账、删库、发邮件这种，得有人点头。

## 真正难的不是那个循环

所有教程里写的第一个 Agent 都是这个形状：

```python
while not done:
    reply = model.chat(messages, tools=TOOLS)
    if not reply.tool_calls:
        break
    for call in reply.tool_calls:
        result = run(call.name, call.args)
        messages.append(result)
```

跑起来很爽，第一次看见它自己调工具的时候会有点小激动。

然后大部分人就不进步了。因为卡住的地方从来不是这个循环，而是**工具写得太烂**。

工具要写好的几条，都是血泪：

- 名字得说人话，`search_orders_by_phone` 远好过 `q2`。
- 描述里要写清楚什么时候该用、什么时候**不**该用。
- 参数尽量用枚举和数字，少给自由文本，因为你永远想不到模型会把日期填成什么。
- 返回值要短、要结构化，别把 100KB 的 HTML 直接甩回去。
- 出错要返回一句人能看懂的错误信息，而不是抛个异常把整个循环炸掉。

说白了，你不是在给模型写工具，你是在给一个**没有常识但非常听话的新同事**写操作手册。手册写得含糊，他就干得离谱。

## 其实你可能天天在用

Cursor 的 agent 模式、Claude Code、Copilot 的编辑代理，全是这一套：读文件、改、跑命令、看报错、再改。区别只在权限——它能不能删你的文件，能不能执行 `rm -rf`。

我自己的感受是，这类工具真正好用的时候，往往不是我让它"帮我做个功能"，而是我给它一个**边界清楚、有验证手段**的活：修这个类型错误、把这个组件拆开、给这个函数补测试。而让它"优化一下这个项目"，结果通常是一地鸡毛。

边界越清楚，它越像专家；目标越模糊，它越像一个特别勤奋但完全不懂业务的实习生。

## 什么时候别用 Agent

也说几句反面的，免得被那些演示视频骗了。

任务固定、步骤明确的，直接写代码，快十倍还免费。需要毫秒级响应的，别碰，模型一次调用就是几百毫秒起步。准确性要求极高、错一次代价很大的，让人来做，或者人加工具，不要把决定权交出去。成本敏感的也算了，一个 Agent 任务动辄十几次模型调用，token 账单是普通问答的十几倍。

还有一种情况：你只是想要一个更自然的人机界面。那用一个对话框就够了，不需要它自己规划、自己调工具。**很多需求根本不需要 Agent，只是"Agent"这个词听起来比较新。**

## 最后

Agent 这个词现在被用得很大，大到快没意义了。有人拿它指一个会自动回邮件的脚本，有人拿它指一整个能自己写代码的团队。

但把包装撕干净，它就是一个很朴素的东西：**让模型能调用工具，并且能根据工具返回的结果，自己决定下一步。**

会写 prompt 的人很多了。会设计工具、会设护栏、知道什么时候该让它停的人，还很少。

后者才是这件事真正的门槛，也大概是我们这些做工程的人，短期内不会被替掉的原因。

---

如果你刚准备动手，建议从一个只有两三个工具的活开始——比如"读这个日志文件，找出报错最多的三处，写进一份 markdown"。别一上来就搞多智能体。你会发现问题全在细节里，而不在架构图上。
