之前调一个接口，页面死活不显示数据。我盯着 Network 面板看了半天：状态码 200，绿的。后端那边也说"我这边没问题啊，你看，200"。后来才发现，响应体里躺着一行 `{"code": 5003, "message": "token expired"}`。

状态码是 HTTP 的语言，业务码是应用自己的语言，两套体系各说各的，我当时却只盯着其中一个。这件事踩过一次之后才真的记住，也是从那会儿开始，我决定把 HTTP 从头到尾认真过一遍——不是背八股，而是把一次请求从敲下回车到字节抵达，完整拆开看。这篇文章就是那次拆解的笔记。

## 它就是一段纯文本

HTTP 没有想象中神秘。用 `curl -v` 发一个请求，你看到的就是它的全部——

```
GET /posts/42 HTTP/1.1
Host: example.com
Accept: application/json
Authorization: Bearer eyJhbGciOi...
```

第一行是请求行：方法、路径、协议版本，用空格隔开。下面每一行是一个头，`名字: 值`。然后一个**空行**，之后（如果有的话）是请求体。

就这么多了。没有二进制魔法，没有隐藏字段。所谓"协议"，就是全世界对这几行文本怎么读达成的一致：第一行是什么意思，头怎么断句，body 到哪算结束。

body 到哪结束这个问题比看上去重要。HTTP 不在 body 末尾写"结束标记"，它靠 `Content-Length` 告诉对方"接下来有 N 个字节，读完就算完"。所以手动拼请求时长度算错，服务器要么傻等，要么把后面的内容当 body 读——很多诡异的传输问题，源头都在这。

响应长一个模样：

```
HTTP/1.1 200 OK
Content-Type: application/json
Content-Length: 38

{"code":5003,"message":"token expired"}
```

注意最后一行。**200，但 body 里写着 token expired。** 先按下不表。

## 状态码只管这一层的死活

状态码很容易被当成"请求成功与否"的总汇报。不是的。它只回答一个问题：**HTTP 这一层的动作，办成了吗？**

- 2xx：办成了。
- 3xx：东西不在这，去别处拿；或者东西没变，用你本地那份。
- 4xx：没办成，**是你的问题**——路径写错（404）、没带证件（401）、证件级别不够（403）。
- 5xx：没办成，**是我的问题**——我这边炸了。

所以 `200 + 业务错误码` 完全合法：HTTP 层面，服务器确实收到了请求，也成功回了你一段 JSON。至于这段 JSON 说"业务失败"，那是应用层自己约定的事，HTTP 管不着。

类似的还有 401 和 403 这对难兄难弟。401 的意思是"我不知道你是谁"，去登录；403 的意思是"我知道你是谁，但你不配"。401 重新登录还有救，403 重试一万次也一样。

还有个低调但极有用的成员：304。意思是"你问我资源变没变，没变，用缓存吧，body 我就不发了"。它是整个 Web 省流量的主力，讲缓存的时候还会碰到它。

## 方法是君子协定

GET、POST、PUT、DELETE 这些方法，本质上是请求方的表态，而不是服务器的强制命令。

GET 说的是"我只是看看，不改变任何东西"——术语叫**安全**；而且"看十次和看一次结果一样"，叫**幂等**。这两个词不是学究概念，它们直接决定别人怎么对待你的请求：CDN 敢缓存它，浏览器敢预取它，爬虫敢无脑遍历它。

所以"用 GET 删数据"不只是风格问题。真出过事：爬虫顺着一个 GET 链接点进去，数据就没了。方法是承诺，你撒谎，生态就会惩罚你。

不过也别把 REST 那套方法语义背得太重。现实里 PATCH 和 PUT 的区别经常被糊掉，POST 更是万能胶水。重要的不是选了哪个方法，而是你有没有按方法的含义对待它。

## 每个请求都是陌生人

HTTP 天生没有记忆。上一个请求是谁发的，这个请求一概不知，服务器处理每个请求都像初次见面。

这个设计当初被骂，后来被感谢。正因为无状态，任何一台服务器都能处理任何一个请求，负载均衡随便扔、随便扩容，不存在"这个用户的请求必须回到之前那台机器"的麻烦。网站能做到高并发，无状态功不可没。

那登录怎么办？答案是把记忆外包给浏览器：服务器回一个 `Set-Cookie`，浏览器把它存起来，之后对这个域名的每个请求都自动带上。Cookie 就是服务器托浏览器保管的小纸条，服务器自己不记账，要用的时候看纸条。

登录态就是这样一张纸条：第一次带着账号密码，验证通过后服务器发回一张写明身份的纸条，此后每次自动出示。Session 和 Token 的区别只是纸条上写什么、谁来核对——前者服务器留底，后者纸条本身就带着全部信息（JWT 就是这么回事）。

## 真正贵的不是流量，是握手

HTTP/1.0 时代，每个请求都要新建一条 TCP 连接：三次握手，配 HTTPS 的话再加两轮，传几百字节，然后挥手告别。建连接的时间常常比传数据还长。

HTTP/1.1 默认复用连接（`Connection: keep-alive` 就是干这个的），一条连接上传很多个请求。但复用带来了新问题：**一条连接上，请求必须排队**。第一个没回来，第二个就得等——哪怕第二个只需要 1KB。这就是队头阻塞。

HTTP/2 的思路很直接：把排队改成并发。一条 TCP 连接上同时跑多个"流"，请求和响应拆成二进制帧交错传输，互不阻塞。

但只解决了一半。HTTP/2 在应用层不排队了，底下那条 TCP 还是一条：网络上丢一个包，TCP 得停下来等重传，所有流一起卡住。于是 HTTP/3 干脆换了底座，用 QUIC（跑在 UDP 上）代替 TCP，把"流"的概念下沉到传输层，一个流丢包不再拖累别的流。

串起来看，三个版本的演进其实只围绕一件事：**怎么让一条连接跑下更多互不拖累的请求。**

## 缓存：最快的请求是不发出去的请求

浏览器和服务器之间有一套心照不宣的省钱机制，分两档。

**强缓存**：服务器第一次响应时交代一句"这文件一个月内不用来问我"（`Cache-Control: max-age=2592000`）。此后浏览器直接用本地副本，请求根本不会发出去。这是最快的一档，快到 Network 面板里显示为 `(disk cache)`。

**协商缓存**：文件可能变了，浏览器带着"我手上这份是 X 版的"去问（`If-None-Match`），服务器一看没变，回一个 304——没有 body，几百字节搞定。变了才回 200 和新内容。

前端部署里那个烂熟的套路——文件名带 hash，比如 `app.a3f9c2.js`——就是这套机制的工程化：带 hash 的文件可以放心给一年强缓存（内容一变 hash 就变），`index.html` 则永远协商缓存，保证用户第一时间拿到新的文件名。两档配合，既快，又不会更新失灵。

## HTTPS 不是另一个协议

常有人说"HTTP 和 HTTPS 是两种协议"，其实 HTTPS 就是"HTTP 套在 TLS 里"。内容一模一样，只是这段文本先被 TLS 加密，再交给 TCP 传输。平时听到的"TLS 握手"发生在那层壳上，跟 HTTP 的语法无关。

它保证两件事：**没人在中间偷看**（加密），**没人在中间篡改**（完整性）。它不保证的事同样值得记住：它证明不了"这个网站是好人"，只证明"你连上的这台机器持有这个域名的证书"。钓鱼网站也可以有合法的 HTTPS 证书——地址栏那把锁从来不是安全背书，只是传输加密的证明。

## 回到那个 200

把整条链路走完，再回头看开头那个问题，排查方式就完全不一样了：

状态码 200，HTTP 层就没问题，别再纠结它；去看 body 里的业务码，那是应用层的事；如果请求压根没出现在 Network 面板，问题在更前面——DNS 没解析、TCP 没连上，或者请求根本没发出去。一层一层剥，每层只回答自己那层的问题。

这大概就是 HTTP 通透的地方：它从来不想包办一切。状态码不管业务对错，HTTPS 不管网站真假，缓存也不会自己判断该不该更新——每一层只把自己这层的约定讲清楚，然后把其余的交给上下层。

理解了这一点，很多"网络问题"就不再是玄学，而是能按层拆开、逐层排查的普通问题了。
