写并发代码最让人不安的地方，是它经常是对的。

你写一段多线程代码，跑十次都对，压测也对，上了线两周没事，然后某个凌晨它错了——而且错完就再也复现不出来。我第一次正面撞上这件事，是因为一个计数器。

场景很朴素：1000 个线程，每个执行一次 `count++`，跑完打印结果。

```java
public class Counter {
    private int count = 0;

    public void increment() { count++; }

    public int get() { return count; }
}
```

预期 1000。实际跑出来是 987，再跑一次 993，偶尔也能跑出 1000，让你怀疑是自己眼花。

从这一行 `count++` 往下挖，基本能把 Java 多线程的主干全串起来。这篇文章就是这条线。

## 线程不是"同时"，是"轮着来"

先纠正一个直觉：哪怕你的机器有 16 个核，1000 个线程也不是 1000 个同时跑。

操作系统把 CPU 时间切成小片，轮流分给各个线程，切得快到你以为是同时。单核机器上跑多线程也一样能"并发"，只是轮换得更明显。真正的"同时"叫并行，它只发生在核数够用的那一刻。

这件事有两个直接推论。第一，线程之间的切换随时可能发生——**在两行代码之间、半行表达式中间，都可能**。第二，切换本身有成本，保存现场、恢复现场都是开销，所以线程不是越多越好，这一点后面讲线程池时还会回来。

## 一行代码，三个动作

`count++` 看着是一步，到了 CPU 那儿是三步：把 count 读进寄存器，加一，写回去。

两个线程交错一下：

```
T1: 读到 count = 5
T2: 读到 count = 5
T1: 算出 6，写回
T2: 算出 6，写回
```

加了两次，结果只加了一次。987 就是这么来的——丢了 13 次，每一次都是某个线程的"写"被别人的"写"盖掉了。

注意这不是"执行顺序乱了"，是"中间被打断了"。这个区分很重要，因为顺序问题后面还会单独出现一次，那是另一种坏事。

一组操作要么全做完、要么一步不做、中间不许插队，这个性质叫**原子性**。`count++` 不满足它，仅此而已，没有更多玄学。

## 但丢更新只是三种病之一

并发 bug 基本落在三个抽屉里：原子性（上面这个）、**可见性**（我写的值你看不见）、**有序性**（编译器和 CPU 把我的指令换了位置）。

可见性反直觉的地方在于：内存明明是共享的，我写进去别人怎么会看不见？因为现代 CPU 每个核心有自己的缓存，线程把值读进寄存器、算完再写回，中间那段窗口里，别的核心看到的就是旧值。JIT 还会火上浇油——它发现循环里没人改这个变量，就把它提升进寄存器，从此另一个线程改一万次，这个循环也看不见。

```java
private boolean running = true;   // 没有 volatile

public void run() {
    while (running) { /* 干活 */ }
}
```

主线程把 `running` 改成 false，这个循环不退。给变量加上 `volatile`，就退了。

至于有序性，最经典的例子是单例的双重检查锁。`instance = new Singleton()` 在字节码层面分三步：分配内存、初始化对象、把引用赋给 instance。第 2 步和第 3 步允许重排——先赋引用、后初始化。于是另一个线程可能在外层判断时看到 instance 非空，直接冲进去用它，而它内部还是空的。

```java
public static Singleton getInstance() {
    if (instance == null) {                        // 第一次检查
        synchronized (Singleton.class) {
            if (instance == null) {
                instance = new Singleton();        // 不是原子的
            }
        }
    }
    return instance;
}
```

这就是"DCL 单例为什么必须加 volatile"的全部原因：volatile 禁止这里的重排。

不过 volatile 也有边界，而且边界很硬：**它保证可见和有序，不保证原子**。`volatile int count; count++` 照样丢更新，读改写三步它一步都不替你合并。所以 volatile 的正确定位是状态标记、一次性发布，不是线程安全的计数器。

这三个抽屉可以用一句话收住，就是 happens-before：**前面的写，对后面读它的人可见**。锁的释放、volatile 的写、线程的 start 和 join，都是这种保证成立的锚点。规则不用背，记住哪里会立锚就行。

## synchronized 锁的是对象，不是代码

方法上写 `synchronized`，等价于把方法体整个包进 `synchronized(this)`；static 方法锁的是 `类.class`。由此立刻能推出一个新手大坑：**两个不同的实例，各自调各自的 synchronized 方法，完全不互斥**——锁挂在对象上，不挂在方法上。你以为是"这个方法同一时刻只能一个人进"，实际是"拿着同一把钥匙的人不能同时进"，而每个对象都是一把独立的钥匙。

另一个容易被忽略的性质是可重入：同一线程已经持有这把锁时再次申请它，不会把自己锁死，锁里记着持有者是谁、重进了几次。所以 synchronized 方法内部再调另一个 synchronized 方法是安全的。

真正影响性能的不是"用不用 synchronized"，而是**锁的范围**。只锁改共享变量的那几行，别把日志、IO、远程调用包进临界区。锁每多持有一毫秒，排在后面的线程就多等一毫秒，这件事比换任何高级锁都更实在。

## 别自己拼，用现成的

计数器这种场景，标准答案是 `AtomicInteger`。它的底层是 CAS：一条 CPU 指令完成"比较旧值、相等才写入"，失败就重读再试，循环往复，术语叫自旋。没有锁、没有挂起线程，竞争不激烈时它比 synchronized 快得多。

```java
private final AtomicInteger count = new AtomicInteger();

public void increment() { count.incrementAndGet(); }
```

CAS 也不是白吃的午餐。竞争激烈时大量线程空转重试，CPU 白烧；它只能保护一个变量，想原子地改两个值就得退回锁；还有 ABA 问题——值从 5 变 7 又变回 5，CAS 看起来成功，其实中间发生过什么它不知道，介意的话用带版本号的 `AtomicStampedReference`。

另一个值得认识的工具是 `LongAdder`。它的思路是把一个计数器拆成一排格子，各线程往各自的格子里加，取值时求和。写多读少的统计场景，它比 AtomicLong 快好几倍，代价是读到的值是"大致准"而不是"实时准"。

## 线程池：被问烂，但真的重要

回到前面说的切换成本。`new Thread` 每次都要申请栈内存、走一遍系统调用，更麻烦的是数量没有上限——流量一冲，几千个线程，光上下文切换就把 CPU 吃空了。线程池干的就是三件事：复用、限流、兜底。

它的执行顺序值得刻在脑子里，因为反直觉：

**核心线程满了，先入队排队；队列也满了，才创建非核心线程；连最大线程数都到了，才触发拒绝策略。**

注意第二步——不是"核心满了就扩容"，是"核心满了先排队"。这个顺序引出一个著名的事故模式：如果你给队列配了无界容量（`LinkedBlockingQueue` 默认就是 `Integer.MAX_VALUE`），那 `maximumPoolSize` **永远轮不到生效**，任务全堆在队列里，内存慢慢涨，直到 OOM。`Executors.newFixedThreadPool` 用的正是这个队列；`newCachedThreadPool` 则是另一个极端，最大线程数是 `Integer.MAX_VALUE`，等于不限流。

这就是为什么阿里规约直接禁掉 `Executors` 的那几个工厂方法，要求老老实实手写 `new ThreadPoolExecutor(...)`——不是为了仪式感，是为了让你被迫看一眼每个参数。

拒绝策略里最值得记住的是 `CallerRunsPolicy`：队列满了，让提交任务的那个线程自己把活干完。听着像惩罚，实际是天然的背压——提交者被占住，上游的生产速度自然就降下来了，比直接丢弃优雅得多。

## 死锁离你没那么远

死锁要凑齐四个条件：互斥、持有并等待、不可剥夺、循环等待。前三个你基本躲不开，唯一能下手的是第四个——循环等待。

真实场景往往就是转账：A 给 B 转，先锁 A 再锁 B；同一时刻 B 给 A 转，先锁 B 再锁 A。两个线程各持一把锁，互相等对方放，等到天荒地老。

解法朴素得不像高级知识：**给所有锁定一个全局顺序**，比如永远按账号 ID 从小到大加锁，两个方向就汇成同一条路，循环等待在结构上不可能出现。另一个办法是 `tryLock` 带超时，拿不到就放弃、退回重来。

排查不用猜。`jstack` 会直接打印 `Found one Java-level deadlock`，连是哪两个线程、分别卡在哪一行都写得清清楚楚。

## ThreadLocal 不是"线程安全的变量"

这个误解太普遍了。ThreadLocal 不是让多个线程安全地共享一个变量，恰恰相反——它让每个线程各持一份副本，互相看不见。它解决的不是"并发改一个值"，而是"一条链路传一个上下文"。

典型用法：请求进来，过滤器把用户身份、traceId 塞进 ThreadLocal，之后这条请求链上的任何一层代码都能直接取到，不用一层层改方法签名。

但在线程池里用它，有一条铁律：**用完必须 `remove()`**。线程是复用的，上一个请求留在里面的值会跟着线程活下去，被下一个请求读到——这不是理论风险，是真实发生过的越权事故。顺带一提，ThreadLocalMap 的 key 是弱引用、value 是强引用，线程不死，value 就一直挂着，内存泄漏也是这么来的。

## 顺便说说虚拟线程

前面的所有痛苦，有一半源于一个前提：**线程很贵**。平台线程 1 比 1 映射到操作系统线程，栈以 MB 计，创建和切换都不便宜，所以才需要池化、限流。

Java 21 的虚拟线程改的就是这个前提。它由 JVM 调度，成千上万个虚拟线程复用少量操作系统线程，遇到 IO 阻塞时主动让出，不去占着内核线程干等。写法还是熟悉的 `Thread.ofVirtual()`，心智模型却接近"一个任务一个线程"，随便开几十万个。

两个清醒的认识：它加速的是**等待**，不是**计算**——IO 密集的服务收益巨大，CPU 密集的任务一点忙帮不上；另外早期版本里在 synchronized 块中阻塞会把载体线程钉住，削弱它的价值，这个限制 JDK 24（JEP 491）已经修掉了。

它不会取代线程池，只是把"为了省线程而池化"这层顾虑拿掉了。该有的同步、该防的竞态，一个都没少。

## 回到 987

现在可以回答开头那个数字了。987 不是偶发故障，是把三步操作当成一步的必然代价——今天丢 13 次，明天换台 64 核机器可能丢 130 次。

把全文收拢一下，其实就是三句话：改共享数据，要么加锁、要么用 CAS，这是原子性；跨线程传递的标记和发布，加 volatile，这是可见性和有序性；实在拿不准，先问一句"**这个变量真的需要被共享吗**"——把共享状态减到最少，剩下的并发问题会自己消失一大半。

多线程难的从来不是语法。难的是你得一直假设：我的下一行代码执行之前，世界可能被别人改过。带着这个假设去写，987 就不会在凌晨来找你。
