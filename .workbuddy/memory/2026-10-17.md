## 统一博客卡片封面尺寸（16:53）

**问题**：列表页里两张卡片的封面大小不一致，封面下方还有大片留空。

**根因**：
1. 封面用的是固定高 `h-28`（112px）+ `md:w-44`（176px），比例 1.57，
   而两张源图都是约 **1.9:1** 的宽图（`rag.jpg` 1117×585、`winter-cat.jpg` 1920×1012），
   被 `object-cover` 硬裁，视觉上就不一致；
2. 卡片高度由左侧文字撑开（标题两行 + 元信息 + 摘要 + 标签行 ≈ 177px），
   封面只有 112px 且顶对齐，多出来的 60 多像素就变成封面下方的空白。

**改法**（`src/components/blog/PostCard.tsx`）：
- 抽出 `COVER_BOX` 常量统一封面尺寸：手机 `aspect-video` 通栏、桌面 `md:w-52` + `md:aspect-[16/10]`。
  **高度全部由 `aspect-ratio` 推导，不再写死 px**，以后换任意比例的图都不会忽高忽低。
- 标题加 `line-clamp-2 min-h-14`（`leading-7` × 2 行 = 56px），保证单行标题也占两行；
- 标签从独立一行挪进「日期 · 阅读时长」那一行（`flex-wrap`），文字块从 ~177px 压到 ~137px，
  和封面 130px 基本齐平，空白基本消失；
- 卡片容器 `md:items-center`，残余高度差变成上下对称的内边距，不再是一侧贴顶一侧留空。

**验证**：`npm run build` 通过；用 `vite preview`（4173 端口）+ 无头 Chrome 截了
1440 / 1100 / 500 三个宽度，封面尺寸一致、无留空。截图在 `.workbuddy/preview/c1-*.png`。
提交 `73be2c9`。

## 循环接缝：交叉淡化（22:00）

用户反馈两条背景视频循环时会「跳一下」，并贴了豆包给的一条 ffmpeg 命令来问是否合理。

### 先量化，再动手

用 PIL 算首帧 / 末帧的逐像素平均绝对差，同时算「正常相邻两帧」的差作为基准 ——
**后者才是判断接缝是否可见的标尺**，绝对值没有意义。

| | 平均差 | 单像素最大跳变 |
|---|---|---|
| 正常相邻两帧（基准）| 0.3~0.7 | 19~42 |
| works-bg 修复前接缝 | 8.39 | 177 |
| works-bg 修复后接缝 | 1.37 | **43** |
| hero 修复前接缝 | 5.85 | 172 |
| hero 修复后接缝 | 1.55 | **34** |

判断标准：**单像素最大跳变回落到基准量级**，肉眼就分辨不出来了。

### 做法（overlay + alpha 淡出）

```
[0:v]split=2[body0][tail0];
[body0]trim=start_frame=0:end_frame=N,setpts=PTS-STARTPTS[body];
[tail0]trim=start_frame=N,setpts=PTS-STARTPTS[tail];
[tail]format=yuva420p,fade=t=out:st=0:d=0.5:alpha=1[tailf];
[body][tailf]overlay=format=auto:shortest=0,format=yuv420p[outv]
```

尾部 0.5 秒淡出后叠到开头 0.5 秒上，输出比原片短 0.5 秒。
**不要加 `shortest=1`** —— 那会让 overlay 在 tail 结束时就截断，输出只剩 0.5 秒。

### 关键洞察：分界点要挑帧间差最小处

交叉淡化后的接缝差异 = 原片「body 末帧 → tail 首帧」的帧间差，这个值无法再压。
所以**分界点可以自由选**，要挑原片里最平滑的位置。

hero 第一次按「末尾 0.5 秒」切（帧 578 处），接缝几乎没改善 —— 因为原片在
**帧 577→578 之间本身就有一处突变**（差 3.29，而前后帧只有 0.02~0.04）。
挪到帧 578|579（差 0.02）立刻生效。

排查方法：逐帧抽出来两两算差，找最小值。抽帧时用 `select=eq(n\,N)` 而不是 `-ss`。

### 坑：hero 的帧时间戳不严格

hero 是 608 帧，但时间戳跨度是 10.08s 而不是 608/60 = 10.13s。
按秒 `trim` 会错位，**一律改用 `start_frame` / `end_frame` 按帧号裁剪**。

#### 三个踩到的坑

1. **RAM 用户建了但没挂策略**：`PutObject` 报
   "no right ... because of bucket acl"，而 `GetObjectMeta` 对不存在的 key 返回
   `NoSuchKey`（跟匿名请求一模一样）—— 这说明请求被当匿名处理，即没有任何 OSS 授权。
   挂上策略后立刻全过。判断密钥本身是否有效：签名错会报

### 首页 3D 背景渐进加载（2026-10-17 21:30）

用户截图问「从纯黑到背景出来能否更快」。实测（playwright + CDP 限速
1Mbps/RTT 120ms）：**FCP 2.7s，背景 10.9s 还没成形**。改完 **FCP 1.2s，静态图 2.1s**。

#### 三个根因（都不是「Spline 太慢」这么简单）

1. **manualChunks 把动态 import 变成了静态依赖**。为了让 109 个碎片 chunk 合并成 12 个，
   加了 `manualChunks` 把 `@splinetool/*` 归组 —— 结果 rolldown 在 index chunk 里
   生成 `import{...}from"./spline-xxx.js"`，还多了条 `modulepreload`。
   浏览器解析首屏 JS 时就开始下那 1MB，占满带宽 9 秒，背景图被挤到 10.9 秒。
   **教训：手动分包会破坏动态 import 的懒加载语义，对「延迟加载的大依赖」一律不要碰。**
2. **`document.readyState` 一旦 complete 就不会回退**。原来用
   `readyState === "complete" ? 立即加载 : 等 load 事件` 判断，但首页 HTML 里
   没有任何图片，load 在 React 插入 `<img>` 之前就触发了 —— 3D 立刻开跑。
   要精确控制顺序，直接挂在目标图片的 `load` 上，别猜文档状态。
3. 3D 没有静态兜底，加载期就是黑屏。

#### 最终结构（`src/components/HeroBackground.tsx`）

| 阶段 | 内容 | 体积 | 时间（1Mbps）|
|---|---|---|---|
| 0ms | 内联 40×23 模糊图，`src/lib/hero-poster.ts` | 386 B | 随 React 首帧 |
| 网络 | 桌面 WebP 57KB / 竖屏 WebP 15KB / JPG 兜底 | — | 0.5s |
| +600ms | Spline 1MB，onLoad 后双 rAF 淡入 | 1MB gz | 8s 后台完成 |

- 手机/平板（`(hover: hover) and (pointer: fine)` 不匹配）、`saveData`、2G/3G
  **完全不加载 3D**（实测请求数 0）。移动端静态图就是终态。
- 竖屏单独出一张 **780×1688** 的图（按 390×844@2x 视口实拍）。横向图裁切后
  砖块被放大且要 58KB，竖图 15KB 还更准。
  拍法：`page.addInitScript` 覆盖 `matchMedia` 强制 `hover:hover` 放行加载。
- 试过在 index.html 里 preload 背景图：FCP 从 1.16s 退到 1.63s，
  图片只提前 153ms，**净亏**，已撤。1Mbps 下「先保文字上屏」比「先保图」划算。

#### 量测方法（重要）

- **`vite preview` 不做 gzip**，用它测中国带宽会严重失真。
  自己写了个 `gzserver.cjs`（node http + zlib.gzipSync）复刻 Pages 的压缩行为。
- CDP `Network.emulateNetworkConditions` 限速对截图采样有干扰：每轮截图+evaluate
  要几百毫秒，采样粒度不能太小。
- 判断「背景是否成形」用截图取**左侧高光区域**统计平均亮度，比全屏非黑像素比更灵敏。
